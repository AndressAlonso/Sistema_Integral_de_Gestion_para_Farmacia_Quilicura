## 5. Base de datos

**No se modificó el esquema. No se crearon ni editaron migraciones.**
Revisión real consultada: 0001_acceso.

Tablas utilizadas: usuario_interno, sucursal, rol, permiso, usuario_rol,
rol_permiso y sesion_interna.
Se conservan IDs UUID, correo único normalizado, claves externas RESTRICT,
sucursal_id NOT NULL y restricciones de fechas de sesión.

El repositorio transforma nombre/correo/activo en name/email/is_active para
mantener una API coherente; no renombra columnas.
Crear usuario y relaciones de rol es una transacción. Editar bloquea la fila
del usuario y modifica solo los campos recibidos.
PostgreSQL resuelve unicidad incluso ante concurrencia; un conflicto del correo
se traduce a 409. Referencias inexistentes devuelven 422.
Desactivar cambia activo=false y revoca sesiones sin eliminar registros.
No se asigna silenciosamente la sucursal del seed.

## 6. Flujo completo

LoginPage → cliente HTTP → POST /api/auth/login → búsqueda PostgreSQL
→ Argon2 → validación activo → JWT → registro de hash/fechas en sesion_interna
→ cookie → RequireAuth consulta /me → menú.

UsersPage → users.api.ts → router autenticado → UserService comprueba permisos
→ PostgresUserRepository → transacción de usuario/roles
→ respuesta pública → React actualiza tabla y contadores.

El hash SHA-256 de un token aleatorio no reemplaza Argon2: Argon2 protege
contraseñas; SHA-256 permite identificar un token de alta entropía sin guardar
su contenido original en la tabla de sesiones.

## 7. Contratos finales

Todos los IDs son UUID representados como strings en JSON.

### Autenticación E1-H1

POST /api/auth/login recibe {email,password}.
POST login y GET /api/auth/me responden:

```json
{
  "user": {
    "id": "UUID",
    "email": "usuario@farmacia.cl",
    "name": "Nombre",
    "permissions": ["usuarios.gestionar", "roles.gestionar"]
  },
  "expires_at": "fecha ISO 8601 con zona horaria"
}
```

No se entrega token en JSON; se entrega mediante cookie.
POST /api/auth/logout responde 204. /me requiere sesión válida.
Errores: 401 credenciales/sesión inválidas, 403 origen no permitido,
422 validación, 429 límite, 500 genérico.

### Usuarios E1-H2

Todos requieren usuarios.gestionar y sesión válida.
Crear exige además roles.gestionar; editar roles diferentes también.

| Método/ruta | Request | Éxito |
| --- | --- | --- |
| GET /api/users | Sin cuerpo | 200: {users,roles,branches,current_user} |
| POST /api/users | {name,email,password,is_active,role_ids:[UUID],branch_id:UUID} | 201: User |
| PATCH /api/users/{UUID} | Uno o más de {name,email,role_ids} | 200: User |
| POST /api/users/{UUID}/deactivate | Sin cuerpo | 200: User inactivo |

User: {id,name,email,is_active,roles:[codigo],role_ids:[UUID],permissions:[codigo],
branch_id,branch_name}. Sin password_hash.
roles del listado: [{id,code,name}]; branches: [{id,name}].
Estos catálogos se entregan dentro del módulo de usuarios; no hay endpoints
administrativos nuevos de sucursales/roles.

Nombre: 1–150 caracteres tras trim. Correo válido hasta 254 y normalizado.
Contraseña inicial: 12–1024 caracteres. Roles no vacíos, sin duplicados y existentes.
Sucursal obligatoria y existente. No se agrega una regla nueva sobre sucursal inactiva.
PATCH no permite password, is_active ni branch_id: no se implementa recuperación,
reactivación ni cambio de sucursal de E1-H4.

Errores: 401 sin sesión, 403 sin permiso/origen rechazado, 404 usuario inexistente,
409 correo ocupado, 422 datos/referencias inválidos, 500 genérico.
Las respuestas no muestran stack traces, SQL ni valores de entrada sensibles.

## 8. Sesiones y seguridad

JWT HS256 con sub UUID, jti aleatorio, iat, exp, iss y aud verificados.
Clave en .env, no en código. Cookie de 9 horas desde el login, no renovación automática.
La fila sesion_interna registra token_hash, usuario y fechas UTC.
La validación exige firma/claims correctos, registro vigente sin revocación y usuario activo.
Logout marca revocada_en. Desactivar revoca todas las sesiones en su transacción.
El registro de sesión bloquea la misma fila de usuario que la desactivación:
una carrera de login/desactivación no deja una sesión utilizable para una cuenta inactiva.

Reiniciar FastAPI ya no cierra sesiones válidas si la clave no cambió.
Los tokens de la versión anterior en memoria no tienen registro y exigen nuevo login.
La cookie /api reemplaza el alcance anterior /api/auth; se limpia el legado.

Límites en memoria por proceso: 8 fallos/correo y 40 intentos/IP por 15 minutos.
No se implementa un limitador distribuido ni se cambia el esquema para ese fin.
Desplegar con HTTPS y COOKIE_SECURE=true queda fuera de la prueba local HTTP.

Incluyen:

- Login válido, desconocido, contraseña incorrecta e inactivo.
- Cookie, permisos, UUID, normalización y errores seguros.
- Token ausente, alterado, expirado, no registrado y claims inválidos.

- Duplicidad al crear/editar y traducción de la restricción real de PostgreSQL.
- Datos obligatorios, UUID/roles/sucursal inválidos y rollback ante fallos.
- Edición sin alterar hash/ID/sucursal.
- Acceso directo sin autenticación/permisos y rechazo de asignación de roles no autorizada.
- Desactivación, revocación, cuenta inactiva y cambio de permisos en sesión existente.

Cada prueba usa una transacción exterior revertida y SAVEPOINTs para los servicios.
