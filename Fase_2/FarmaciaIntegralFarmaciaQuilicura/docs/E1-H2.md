# E1-H2 — Gestión de usuarios internos

## 1. HU implementada

Como Administrador, crear, actualizar y desactivar usuarios internos para controlar
los accesos del personal. AC1: creación con datos válidos y correo disponible.
AC2: rechazo de correo duplicado. Se verifican además edición, desactivación y
autorización en backend.

## 2. Qué se implementó

- Menú lateral y cabecera compartidos inspirados en el mockup, usando el logo existente.
- `/admin/users`: listado real, estadísticas, búsqueda por nombre/correo y filtros por rol/estado.
- Formularios accesibles mediante `dialog`: crear y editar; confirmación para desactivar.
- Campos de creación: nombre, correo, contraseña inicial, roles y estado activo.
- Edición: nombre, correo y roles del catálogo temporal. Desactivación separada, sin eliminación física.
- Errores comprensibles, estados de carga y bloqueo de envíos repetidos.
- FastAPI exige sesión válida y rol `ADMINISTRADOR` en todos los endpoints de usuarios.
- Escritura JSON atómica con exclusión mutua dentro de un único proceso.
- Login existente reutilizado: una cuenta creada puede autenticarse si está activa.
- La desactivación bloquea login, `/me` y operaciones protegidas aunque el JWT no haya expirado.

Las demás opciones del menú muestran contenido vacío: Resumen, Inventario,
Productos, Transferencias, Pedidos Online, POS/Ventas, Caja, Promociones,
Auditoría, Reportes y Configuración. No simulan funciones de otras historias.
El cierre de sesión funciona desde todas esas pantallas.

Se omiten sucursal y último acceso del mockup porque no hay datos reales para
esos campos en el alcance actual. No se inventan cifras, sucursales ni identidad
de la persona conectada. No se agregan CRUD de roles/permisos, recuperación de
contraseña, cambio de contraseña ni reactivación de cuentas.

## 5. Base de datos y persistencia

**No se modificó el esquema.** No se crearon tablas ni migraciones PostgreSQL.
Se mantiene JSON por decisión explícita del usuario.

El modelo temporal conserva IDs enteros y añade `name` y `roles`. Los archivos
anteriores siguen siendo legibles: nombre vacío y roles vacíos por defecto.
No se concede automáticamente rol administrador a cuentas antiguas.

`UserRepository` expresa las operaciones que necesita el servicio. El adaptador
`LocalUserRepository` implementa lectura, creación y actualización. Al escribir:

1. Adquiere un `RLock` del repositorio compartido por el proceso.
2. Lee la versión actual del archivo y comprueba ID/correo.
3. Aplica únicamente los campos solicitados.
4. Valida correo único sin distinguir mayúsculas.
5. Escribe un archivo temporal, hace flush/fsync y lo reemplaza atómicamente.

Esto evita archivos parciales, IDs duplicados y pérdida de modificaciones
concurrentes dentro del mismo proceso. **No ejecutar con varios workers ni editar
el JSON manualmente mientras se está usando.** No es persistencia de producción.

PostgreSQL deberá implementar la misma interfaz y garantizar unicidad y
transacciones. El servicio conserva las reglas; la BD también protege integridad.
La transición a UUID, relaciones Usuario–Rol–Permiso y `SesionInterna` del diagrama
requiere una propuesta y aprobación posterior. No se reinicia ningún historial
de migraciones previo.

## 6. Flujo completo

1. `LoginPage` autentica por FastAPI y el navegador recibe la cookie HttpOnly.
2. `RequireAuth` consulta `/api/auth/me` antes de mostrar el menú.
3. Al elegir Usuarios, `UsersPage` llama a `users.api.ts` → `GET /api/users`.
4. El router valida JWT, sesión registrada, cuenta activa y rol Administrador.
5. `UserService` autoriza y utiliza `UserRepository` para obtener los datos.
6. El adaptador lee JSON y la API devuelve exclusivamente campos públicos.
7. Al guardar el formulario, React hace validaciones básicas y envía POST/PATCH.
8. Pydantic valida datos obligatorios, correo, roles y límites de longitud.
9. El servicio comprueba unicidad y genera Argon2 para la contraseña inicial.
10. El repositorio vuelve a comprobar unicidad dentro del bloqueo y persiste.
11. La API devuelve el usuario guardado; React actualiza tabla, filtros y contadores.
12. Un 409 mantiene abierto el formulario para corregir el correo.
13. Desactivar conserva el usuario con `is_active=false`; los siguientes accesos
    autenticados lo consultan de nuevo y se rechazan.

Los estados del listado, filtros, carga y mensajes están en `UsersPage`.
Los valores del formulario están en `UserDialog`. El transporte común envía
cookies, controla el tiempo de espera y convierte fallos HTTP a mensajes seguros.
No se utiliza `localStorage` como prueba de autenticación.

## 7. Contratos finales

Todos los endpoints siguientes pertenecen a E1-H2, requieren la cookie de sesión
válida y rol `ADMINISTRADOR`. Los nombres `name`, `email`, `roles`, `is_active`
se conservan coherentes con la implementación temporal.

| Método/ruta | Entrada | Éxito |
| --- | --- | --- |
| `GET /api/users` | Sin cuerpo | 200: `{users: User[], roles: [{code,name}], current_user: User}` |
| `POST /api/users` | `{name,email,password,roles,is_active}` | 201: `User` |
| `PATCH /api/users/{id}` | Uno o más de `{name,email,roles}` | 200: `User` |
| `POST /api/users/{id}/deactivate` | Sin cuerpo | 200: `User` con `is_active:false` |

`User`: `{id:number,name:string,email:string,roles:string[],is_active:boolean}`.
Catálogo temporal: `ADMINISTRADOR`, `CAJERO`. Crear/editar no permite roles
desconocidos ni listas vacías/duplicadas. Nombre: 1–120 caracteres tras trim;
correo válido hasta 254; contraseña inicial: 12–1024, nunca recortada silenciosamente.
No se admite actualizar contraseña, hash, ID ni estado mediante PATCH.

Errores: 401 sesión inválida/expirada o cuenta inactiva; 403 falta de rol u origen
rechazado; 404 usuario objetivo inexistente; 409 correo duplicado; 422 datos
inválidos; 500 error interno genérico. Formato: `{detail:string}`. CORS inválido
puede devolver 400 en preflight. No se retornan datos internos de excepciones.

`POST /api/auth/login`, `GET /api/auth/me` y `POST /api/auth/logout` mantienen
los cuerpos públicos de E1-H1. La cookie cambia de `Path=/api/auth` a `Path=/api`:
los consumidores web deben volver a iniciar sesión para usar los nuevos endpoints.

## 8. Seguridad

- Argon2 almacena una representación verificable, no la contraseña original.
- JWT firmado HS256, con expiración de 9 horas y claims mínimos; secreto desde `.env`.
- Cookie HttpOnly y SameSite Strict; `Secure=false` exclusivamente en HTTP local.
- Sesiones registradas en memoria: logout revoca el identificador; reiniciar el
  proceso invalida sesiones. No es un JWT que se acepte solo por estar firmado.
- Cada operación vuelve a consultar cuenta y roles. Ocultar botones no autoriza.
- Orígenes explícitos para CORS y comprobación de Origin en escrituras.
- Respuestas no incluyen hashes, contraseñas, tokens ni detalles internos.
- Los datos de desarrollo y secretos se excluyen de Git.

## 10. Cómo ejecutar — Windows PowerShell

Desde la raíz del frontend, instalar dependencias:

```powershell
npm.cmd ci
Set-Location backend
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

Si ya tienes `.env` y `data/users.json`, consérvalos y ejecuta:

```powershell
.venv\Scripts\python.exe -m app.seed_dev --upgrade-e1-h2
```

En un checkout nuevo sin `.env`, crear configuración y secreto local:

```powershell
Copy-Item .env.example .env
$jwtLocalKey = .venv\Scripts\python.exe -c 'import secrets; print(secrets.token_urlsafe(48))'
(Get-Content .env) -replace '^JWT_SECRET_KEY=.*$', "JWT_SECRET_KEY=$jwtLocalKey" | Set-Content .env -Encoding utf8
Remove-Variable jwtLocalKey
.venv\Scripts\python.exe -m app.seed_dev
```

El seed solicita contraseña sin mostrarla. Para reproducir los ejemplos locales,
puedes usar `Desarrollo-E1H1!2026`, exclusivamente en desarrollo. Si elegiste otra,
utiliza esa contraseña: no hay una contraseña universal incrustada en el backend.

Terminal 1, desde `backend/`:

```powershell
.venv\Scripts\python.exe -m uvicorn app.main:create_app --factory --reload --host 127.0.0.1 --port 8000
```

Terminal 2, desde la raíz del frontend:

```powershell
npm.cmd run dev -- --host 127.0.0.1
```

Pruebas desde la raíz:

```powershell
npm.cmd run lint
npm.cmd run build
Set-Location backend
.venv\Scripts\python.exe -m ruff check app tests
.venv\Scripts\python.exe -m pytest -q
```

Para evidencia exportable del Sprint:


## 11. Prueba manual

1. Abrir `http://127.0.0.1:5173/login`.
2. Entrar con `interno@farmacia.cl`, contraseña local elegida en el seed. En el
   entorno verificado: `Desarrollo-E1H1!2026`. El seed le asigna Administrador.
3. Se muestra Resumen vacío con menú. Abrir Usuarios o `/admin/users`.
4. Crear una cuenta ficticia con nombre, correo nuevo, contraseña de 12 o más
   caracteres, rol Cajero y estado activo. Debe aparecer y aumentar el contador.
5. Recargar: la cuenta debe persistir.
6. Intentar otro usuario con el mismo correo cambiando mayúsculas: conflicto sin duplicar.
7. Editar nombre/correo; recargar y comprobar persistencia. Intentar correo ocupado: conflicto.
8. Iniciar sesión con la cuenta nueva en una ventana privada. Funciona el login;
   el acceso directo a `/admin/users` responde sin permiso.
9. Desde la ventana del administrador, desactivar esa cuenta. Al recargar la
   ventana privada, su sesión se rechaza. Tampoco puede volver a iniciar sesión.
10. `inactivo@farmacia.cl` con la contraseña del seed debe recibir el mensaje
    genérico de credenciales incorrectas.
11. Visitar las demás opciones: contenido vacío, menú persistente y opción activa resaltada.
12. Cerrar sesión y abrir `/admin/users`: debe volver al login.

Capturas útiles: listado, formulario, éxito de creación, conflicto de correo,
confirmación de desactivación, acceso denegado del Cajero y salida de pytest.

## 12. Impacto para el equipo

- Actualizar ramas e integrar mediante revisión por otro integrante.
- No hay migraciones, nuevas dependencias ni nuevas variables obligatorias.
- Cada integrante debe ejecutar su seed o la actualización de fixtures; JSON
  y `.env` no se comparten mediante Git.
- Volver a iniciar sesión por el cambio de alcance de cookie.
- La ruta del prototipo de inventario cambia a `/prototypes/inventory`.
- Flutter no cambia su contrato de login; nuevos consumidores deben respetar
  la autenticación por cookie existente.
- Al migrar PostgreSQL, sustituir el adaptador y garantizar restricciones y
  transacciones; revisar UUID y relaciones con el equipo antes de crear migraciones.

## 13. Decisiones y pendientes reales

- JSON, IDs enteros y administrador de desarrollo: adaptación temporal aprobada.
- Catálogo mínimo Administrador/Cajero para crear cuentas según rol. No es E1-H3 completo.
- Los roles se consultan del usuario; no se confía en roles enviados por el cliente
  como prueba de autorización, ni se fijan dentro del JWT.
- La edición no reactiva cuentas ni cambia contraseñas: esas funciones no se incluyeron.
- Se permite desactivar la propia cuenta y cambiar sus roles; no se inventó una
  regla de bloqueo del último administrador. Recuperar un entorno de desarrollo
  sin administradores requiere una intervención explícita en sus fixtures.
- Falta persistencia definitiva PostgreSQL/UUID/sesiones del diagrama y auditoría
  persistente compartida; deben definirse y aprobarse antes de producción.
- Falta revisión visual en navegador y revisión de otro integrante antes de integrar.
- Este avance cubre E1-H2 sobre la persistencia temporal acordada; no certifica
  preparación para producción ni historias futuras.
